# Documented exceptions

The project's bar is FedRAMP Moderate (NIST SP 800-53 Rev. 5 Moderate baseline). These are the places where this repo, or the tutorial it serves, deliberately falls short. The standing rule is that a bad practice the tutorial needs stays, for ease, but only with its remediation written down, and a gap is acceptable only when it is documented and quantified.

Floci-vs-AWS differences are a separate list, in [GAPS.md](../GAPS.md). Static-analysis findings suppressed for these reasons carry the exception number in their `#checkov:skip` comment.

## From the tutorial

| # | What | Controls | Scope, quantified | Remediation in production |
|---|---|---|---|---|
| E-1 | Root SSH from the jumpbox to every cluster machine (lab 3) | AC-6, IA-2, AC-17 | 3 machines accept the jumpbox's root key. Keys only: `PasswordAuthentication no` everywhere, and the root key never leaves the jumpbox (only its public half goes through SSM). | Named users with `sudo`, short-lived keys from EC2 Instance Connect or SSM Session Manager, and no direct root login. |
| E-2 | A hand-made certificate authority whose private key sits in `/root/kubernetes-the-hard-way` on the jumpbox and on `server` (lab 4) | SC-12, SC-17 | 1 CA key (RSA 4096), 2 copies on disk, unencrypted; 3653-day certificates. | AWS Private CA or cert-manager with a KMS- or HSM-backed issuer; 1-year or shorter certificates with rotation. |
| E-3 | Client keys and kubeconfigs with embedded keys copied by `scp`, and an encryption key in a file (labs 4 to 6) | IA-5, SC-28 | About 20 private keys on the jumpbox, copies on each machine; `encryption-config.yaml` holds the etcd encryption key in plain text on `server`. | An identity provider (OIDC) for people, short-lived credentials for components, and a KMS provider for etcd encryption. |
| E-4 | Pre-release components: containerd 2.1.0-beta.0, runc 1.3.0-rc.1, etcd 3.6.0-rc.3 (lab 2's downloads list) | SI-2, CM-2 | 3 of the 11 downloaded components are pre-releases. | Released, patched versions from a vetted internal mirror, verified by checksum and signature. |
| E-8 | etcd serves clients over plain HTTP on `127.0.0.1:2379` (lab 7's unit) | SC-8 | Loopback only on `server`; nothing else can reach it. | Mutual TLS for etcd clients and peers. |

## From this repo

| # | What | Controls | Scope, quantified | Remediation in production |
|---|---|---|---|---|
| E-5 | One home region: no cross-region replication of the state bucket or the log buckets | CP-6, CP-9 | 6 buckets (state, CloudTrail, Config, and the access-log bucket of each) in one region. | S3 replication to a second region, and Object Lock on audit logs. |
| E-6 | `bootstrap/` keeps local Terraform state | CM-6 | 1 state file per target (`bootstrap/terraform.tfstate` for floci, `bootstrap/terraform.tfstate.d/aws/` for AWS, so one target never refreshes the other's resources), holding bucket and key names only, no secrets. | Create the state bucket from an account-vending pipeline, or migrate this state into the bucket after the first apply. |
| E-7 | GuardDuty runtime monitoring is off | SI-4 | Off for all 4 instances; it installs an agent and is billed per vCPU. S3 and EBS malware protection are on. EBS scans of the 6 volumes encrypted with the workload key rely on the GuardDuty malware-protection service-linked role's AWS-managed policy, which the key policy honours by delegating to IAM (AWS documents that role's policy as granting `CreateGrant` and re-encryption on customer-managed keys not tagged `GuardDutyExcluded=true`: GuardDuty user guide, "Service-linked role permissions for Malware Protection for EC2"); tagging that key `GuardDutyExcluded=true` turns the scans off. An offline guard keeps the delegation in the key policy. Not yet confirmed by a scan on AWS (floci has no GuardDuty scanning; `kthw-q85.16`). | Turn on runtime monitoring. |
| E-9 | Cluster members accept all traffic from each other and from the pod range | SC-7 | 1 security group, 4 rules (self and `10.200.0.0/16`, in and out). KTHW's control plane, kubelets and pod routes need these. | Narrow to the ports Kubernetes uses (6443, 10250, 2379-2380, the CNI's), and add network policies inside the cluster. |
| E-10 | Machines reach the internet on TCP 80 and 443 to any address, through the NAT gateway | SC-7(5) | 2 security groups, 4 rules. Needed for Debian packages, GitHub releases and container images. | An egress allowlist (AWS Network Firewall or a proxy) and VPC endpoints for AWS services. |
| E-11 | Instances reach SSM Parameter Store through the NAT gateway | SC-7 | 4 instances. Each re-checks its keys at boot and every 5 minutes: 10 `GetParameter` calls per round across the 4 machines (2,880 a day), plus 1 `PutParameter` per machine when its key changes (first boot, rebuild). | Interface VPC endpoints for SSM. |
| E-12 | The machines run no SSM agent | CM-8, SI-2 | 4 instances not managed by Systems Manager. Access is by EC2 Instance Connect by design. | Install the SSM agent for patching, inventory and Session Manager. |
| E-13 | Security alarms and findings publish to an SNS topic with no subscriber | IR-6, SI-4(5) | 1 topic, 16 alarms and 2 finding rules (GuardDuty medium and up; new active Security Hub HIGH and CRITICAL). | Subscribe the security team's mail or a SIEM. |
| E-14 | The access-log buckets do not log access to themselves | AU-2 | 3 buckets. Logging a log bucket into itself recurses. | Log them into a separate, central log archive account. |
| E-15 | Bedrock is not covered by CloudTrail data events, and the Config role can read Bedrock configuration | AU-2, AC-6 | Bedrock is not used. The read access comes from the AWS-managed `AWS_ConfigRole` policy. | Add Bedrock data events if Bedrock is adopted. |
| E-16 | The root-SSH trust anchor is an SSM parameter: whoever can write it can add a root key to every cluster member | AC-6, IA-5, SC-12 | 4 parameters under `/kthw/` (the jumpbox's root public key, 3 host keys), SecureString under the workload key; 3 machines append the jumpbox value to root's `authorized_keys`. Nodes accept only a SecureString they can decrypt with that key (an explicit deny blocks every other key, `aws/ssm` included), so a forger needs `ssm:PutParameter` on the parameter **and** `kms:Encrypt` on the workload key. The key policy delegates to IAM, so any principal granted `kms:*` or `kms:Encrypt` on `*` in IAM, typically account administrators, still can. Every write and delete raises the `ssm-ssh-key-changes` alarm (expected at first boot, rebuild, apply and destroy). | A key policy that grants `kms:Encrypt` for the jumpbox parameter's encryption context to the jumpbox role only, without IAM delegation; or a signed value; or no root SSH at all (E-1's remediation). |
| E-17 | AWS endpoints are the standard ones, not FIPS 140 endpoints | SC-13 | All AWS API calls: Terraform, the AWS CLI in the scripts, and the machines' SSM helper (`ssm.<region>.<partition DNS suffix>`). | `AWS_USE_FIPS_ENDPOINT=true` for Terraform and the CLI, the `ssm-fips` host for the helper, in a region that offers FIPS endpoints. |
| E-18 | No backups of the machines' volumes | CP-9, CP-10 | 6 volumes (4 root, 2 containerd), no snapshots and no AWS Backup plan. The cluster holds no data of record: Terraform and the tutorial rebuild it. | An AWS Backup plan (or a Data Lifecycle Manager policy) with the retention the organization's CP-9 schedule sets, and a tested restore. |
| E-19 | Security Hub runs in the home region only | CA-7, SI-4 | 1 of the 17 default regions. GuardDuty, AWS Config, EBS default encryption and IAM Access Analyzer run in all 17; Security Hub's standards checks are billed per region and add nothing a learning account needs beyond the home region. | Enable Security Hub in every region with a cross-region finding aggregator in the home region. |
